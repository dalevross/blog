Over the last two days, I built **doorvox**: a thin webhook and relay service that lets a delivery app turn a status change into an Alexa announcement.

It started with something smaller and more human than a product roadmap. I was stressed about missing an Instacart grocery delivery—the kind of low-grade anxiety where you are half-listening for a knock while trying to do something else. I mentioned it to my therapist, who pointed out that I had the skills to build a solution instead of simply living with the friction.

That comment stuck with me.

## The gap I wanted to close

Delivery apps have no simple, carrier-neutral way to make Alexa speak when an order changes to **delivered**. Amazon's Delivery Tracker API is intended for merchants using Amazon Pay at checkout, which leaves out many grocery shoppers, local couriers, and smaller delivery services. Instacart does not currently offer an Alexa integration for this either.

So the problem became straightforward to describe:

> When a delivery backend knows an order has arrived, how can it make the customer's Alexa say so—without making that backend take on Amazon credentials, Alexa protocols, or a pile of smart-home infrastructure?

The answer is doorvox.

## What doorvox is

doorvox is a carrier-agnostic webhook and relay layer. A delivery app sends one event when an order is marked delivered; doorvox handles the Alexa-facing work.

I designed it around four priorities:

- **Trivial integration:** A delivery app should be able to add it in an afternoon with one webhook call.
- **Credential isolation:** The delivery app never sees or stores a customer's Amazon or Alexa tokens.
- **Privacy by default:** The standard message is simply “Your delivery has arrived.” Item details are optional and should require an explicit customer choice.
- **Open core, hosted convenience:** The SDK and webhook contract are MIT licensed and can be self-hosted, while a hosted relay can serve teams that do not want to operate OAuth and token infrastructure.

## What I built

The proof of concept has two open-source components and one real integration:

- **`doorvox-sdk`:** A small TypeScript client with `notifyDelivered()` and `getLinkUrl()` methods for delivery backends.
- **`doorvox-relay`:** A Node/Express reference service using SQLite for persistence. It is the only component that touches Alexa credentials, deduplicates retried webhooks, and can fall back to push or SMS when no Alexa account is linked.
- **A real integration:** I wired the client into an existing property-transfer app as a stand-in delivery backend. Adding doorvox to its transfer-completion flow took about ten lines of code—the “few lines of integration” goal in practice.

The basic path is deliberately boring:

```text
Delivery completed
        ↓
Delivery app backend
        ↓
    doorvox SDK
        ↓
  doorvox relay
        ↓
Alexa Event Gateway
        ↓
Customer's Alexa device
```

Boring is good here. The delivery app should not need to understand Alexa.

## The part that was much harder than expected

The first working version used Alexa's **Proactive Events API** with the `AMAZON.OrderStatus.Updated` event. Alexa accepted the event, and the demo appeared to work—until I realized what “working” meant in this API.

It produced a chime and a notification light. The customer still had to ask, “Alexa, what are my notifications?” before hearing the message.

That is useful for some products, but it does not solve the doorbell-style problem. I wanted the speaker to say the delivery had arrived without another prompt.

Getting there meant pivoting to a **Smart Home skill** using `Alexa.ProactiveNotificationSource`. That uncovered several details I would not have known without building the entire path:

- I needed an AWS Lambda to handle Alexa's Discovery and Authorization protocol.
- Login with Amazon involved two distinct credential pairs: one for the customer-facing consent flow and another for exchanging the resulting grant for tokens. Mixing them produced an unhelpful `invalid_grant` error.
- The Discovery response needed both `notificationConditions` and `semantics.stateMappings`. Without them, Alexa accepted each state update and showed it in the customer's Alexa app, but silently declined to speak.
- Even with the state model correct, real spoken announcements through this API appear to require Amazon skill certification. A development skill can update the device state successfully and still produce no audio.

This was not one dramatic bug. It was a chain of individually reasonable assumptions that only failed once the complete system was running.

## A practical route to spoken announcements today

I did not want the proof of concept to stop at “the device state changed.” So doorvox also exposes the virtual device as an **`Alexa.ContactSensor`**.

Alexa Routines can use contact sensors as triggers without waiting for skill certification. The customer creates a routine that says a generic phrase when the virtual sensor opens, and a delivered webhook triggers that state change.

There is a trade-off:

- **Smart Home proactive notifications** can support dynamic, branded language such as “Your [App] delivery has arrived,” but the skill needs certification before that speech is available to customers.
- **The ContactSensor and Routine path** works now without certification, but the customer configures the spoken phrase and it is generally more generic.

For a proof of concept, a working announcement today beats a theoretically richer announcement later.

## Solving account pairing without sharing Alexa credentials

Another subtle problem was identity. Alexa owns the skill-linking interface, so the relay does not automatically know which customer in a delivery app belongs to the Alexa account that was just linked.

The solution is a short pairing code embedded in the discovered device's name:

1. The customer enables the doorvox Smart Home skill and completes Login with Amazon.
2. Alexa discovers a doorvox device whose name includes a short code.
3. The customer enters that code in the delivery app's settings.
4. The delivery app sends the code and its own customer reference to doorvox from the backend.
5. Future delivery events for that customer reference are routed to the linked Alexa devices.

The code can rotate on a schedule, reducing the chance of collisions, without breaking a claim the customer has already completed. The same Alexa account can also be linked to a second delivery app later without starting over.

The important boundary remains intact: the delivery app handles one opaque pairing code, never an Alexa token.

## Integrating doorvox into a delivery backend

The runtime integration is intentionally small:

```ts
import { Doorvox } from "doorvox-sdk";

const doorvox = new Doorvox({ apiKey: process.env.DOORVOX_API_KEY });

// Fire this when the driver or shopper marks the order delivered
await doorvox.notifyDelivered({
  orderId: "ord_8x2f9",
  carrierCode: "CUSTOM_SHOPPER",
  customerRef: "cust_a91k2",
  itemSummary: "Groceries (12 items)", // optional; omit by default for privacy
});
```

The one-time customer association is also server-side:

```ts
await doorvox.claimSmartHomeLink({
  code: submittedCode,
  customerRef: "cust_a91k2",
});
```

That is all the delivery app needs. No Amazon developer account, Lambda, or Alexa-specific code is required on its side. That complexity lives inside the relay.

## Where it stands after two days

The full technical pipeline is proven end to end:

```text
webhook → relay → Alexa Event Gateway → device state in the Alexa app
```

Spoken announcements work today through the ContactSensor and Routine path. The path for dynamic, branded announcements is built, but actual speech is still gated behind Amazon's skill-certification process, which I have not pursued yet.

This is a proof of concept, not a production-hardened service. Before a real certification submission, I would want to improve persistence, linking-flow reliability, failure handling, observability, and the account-linking experience.

Still, the central idea survived contact with the real platform: a delivery app can add an Alexa announcement with a small backend integration, while keeping Amazon credentials completely out of its system.

## What I learned

The official path and the useful path are not always the same thing.

The Proactive Events API sounded like the obvious fit, but it delivered a notification rather than the unprompted speech I needed. The Smart Home path could model the right behavior, but the missing Discovery declarations and certification gate were only obvious after tracing successful requests that produced silence. The ContactSensor workaround was less expressive, but it made the core experience real.

That is the value of building the full loop. Documentation can tell you which APIs exist. Only an end-to-end prototype tells you which one actually solves the human problem.

And the human problem was always the point: I wanted to stop half-listening for a grocery delivery while trying to do something else. Two days later, a delivery webhook can make Alexa tell me it is at the door.
